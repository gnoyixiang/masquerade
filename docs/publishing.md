# Publishing to the Chrome Web Store

Masquerade's `Publish to Chrome Web Store` workflow is manual. It first runs
the same test, build, package, zip-integrity, and JavaScript syntax checks as
CI. Only a successful validation job can reach the publish job, and the publish
job also requires explicitly choosing the `publish` workflow input. The default
is `false`, which makes it possible to run validation and download the package
without publishing. The publish job uses the `chrome-web-store` GitHub
Environment, so configure required reviewers there for a second approval gate.

The workflow uploads `masquerade.zip` to an existing Chrome Web Store item and
calls the Chrome Web Store API v2 `publish` method. That submits the item for
Chrome Web Store review; it does not bypass review or guarantee immediate
public availability.

## One-time Google setup

Use the Google account that owns or manages the Chrome Web Store item. Chrome
requires 2-step verification for developers who publish or update an existing
extension. For a new item, complete the Store listing and Privacy tabs in the
Developer Dashboard before using the API.

1. Open [Google Cloud Console](https://console.cloud.google.com/), create or
   select a project, search for **Chrome Web Store API**, and enable it.
2. Open **APIs & Services → OAuth consent screen**. Choose **External**, create
   the app, provide the app name, user-support email, and developer contact
   information, then save. You can skip the scopes screen. Add the Google
   account that owns the store item as a test user.
3. Open **APIs & Services → Credentials → Create credentials → OAuth client ID**.
   Choose **Web application**, give it a name, and add this exact authorized
   redirect URI:

   ```text
   https://developers.google.com/oauthplayground
   ```

   Save the resulting client ID and client secret.
4. Open the [Google OAuth 2.0 Playground](https://developers.google.com/oauthplayground).
   Select the settings gear, enable **Use your own OAuth credentials**, and
   enter the client ID and client secret from step 3.
5. In the Playground's custom scope field, enter:

   ```text
   https://www.googleapis.com/auth/chromewebstore
   ```

   Click **Authorize APIs**, sign in with the Chrome Web Store owner/manager
   account, and click **Exchange authorization code for tokens**. Save the
   refresh token; the workflow uses it to obtain short-lived access tokens.
6. In the [Chrome Web Store Developer Dashboard](https://chrome.google.com/webstore/devconsole),
   open **Publisher → Settings** and copy the **Publisher ID**. Copy the
   extension's 32-character item ID from its dashboard page or store URL.

The API account and the Google Cloud project account may be different. The
OAuth Playground authorization must use an account that can manage the target
Chrome Web Store item.

## Required GitHub secrets

In the repository, open **Settings → Secrets and variables → Actions → New
repository secret** and add all five secrets with these exact names:

| Secret | Value |
| --- | --- |
| `CWS_CLIENT_ID` | OAuth 2.0 client ID from Google Cloud |
| `CWS_CLIENT_SECRET` | OAuth 2.0 client secret from Google Cloud |
| `CWS_REFRESH_TOKEN` | Refresh token generated by OAuth Playground |
| `CWS_PUBLISHER_ID` | Publisher ID from Developer Dashboard → Publisher → Settings |
| `CWS_EXTENSION_ID` | The existing Chrome Web Store item's 32-character ID |

Do not commit these values or put them in workflow files. The workflow sends
the refresh token to Google's OAuth token endpoint, then uses the resulting
access token for the v2 upload and publish calls.

## Protected environment setup

1. Open the repository's **Settings → Environments** and create an environment
   named exactly `chrome-web-store`.
2. Under **Deployment protection rules**, add **Required reviewers** and select
   the person or team that must approve a release. Optionally configure a wait
   timer and deployment branch rules; restrict deployments to `main` if that is
   your release policy.
3. Keep the five values above as repository secrets, or place them as
   environment secrets if you want them available only after the environment
   approval gate. If using environment secrets, create the same exact names in
   the `chrome-web-store` environment instead of repository secrets.

## Publishing a release

1. Merge the intended version to `main` and confirm the validation workflow is
   green.
2. Open **Actions → Publish to Chrome Web Store → Run workflow**, select
   `main`, set `publish` to `true`, and start it. Leave `publish` as `false` if
   you only want to validate and download the package artifact.
3. Approve the `chrome-web-store` environment deployment when GitHub pauses for
   review.
4. Check the workflow log for the successful upload and the message that the
   publish request was submitted. Finish any review or listing actions in the
   Chrome Web Store Developer Dashboard.

The package is generated only inside the workflow (and locally by
`npm run package`). `masquerade.zip` is intentionally ignored by git.

API reference: [Use the Chrome Web Store API](https://developer.chrome.com/docs/webstore/using-api).
